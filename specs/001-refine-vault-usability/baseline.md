## Overflow reproduction and diagnosis

The untouched application was checked with Privacy Mode off, the first login item open,
filters expanded and both dates shown. A 24-case English/Arabic × light/dark matrix covered
1280 × 800, 1440 × 900, 1440 × 600, 1024 × 768, 768 × 844, and 320 × 844.
This is a scoped reproduction, not a full new-feature layout acceptance run.

At every tested desktop size, document scroll height was **1135 pixels in English** and
**1150 pixels in Arabic**, exceeding the viewport. The workspace, editor footer and pagination
were already bounded correctly. The responsible Notes label in `ItemEditor.vue:122` uses
the absolute-positioned `sr-only` utility inside `.editor-scroll`, whose position is static
(`src/style.css:312`). Its containing block is BODY, so its offscreen static position escapes
the scroll region and enlarges the page's overflow area. Privacy-on removes this label.

A second bounded diagnostic at 1280 × 800 tested all four locale/theme pairs:

- Untouched: the label's containing block was BODY; document height 1135/1150.
- Temporary browser-only `.editor-scroll { position: relative; }`: containing block became
  the editor scroll region, document height returned to 800, and both footers still ended at 800.
- Removing that temporary style restored the same overflowing height in every pair.

The planned root-cause fix is to establish that scroll region's positioning context, keeping
the accessible label and existing scrolling behavior. No global body clipping is needed.
Re-test the full long-content/optional-fields/zoom matrix after implementation; this diagnosis
does not rule out distinct future layout defects. No source CSS was modified by the experiment.
